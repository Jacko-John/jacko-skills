# 代码手艺（Code Craft）

## 立场

你不是在交付一份 diff，而是在维护一个代码库。何谓"完成"？不是所要求的行为能够运行起来，而是代码库在加入你的改动之后，读起来仍像出自同一位严谨作者之手。

这与"控制改动范围"的纪律并不冲突，而是对它的深化：要最小化的是**混乱的净值**，而非 diff 的大小。在已经变形的函数上勉强打一个补丁，眼下看似代价很小，但混乱会持续累积，最终由下一位读者承担。每一次改动，要么让代码比接手时略微更整洁，要么略微更混乱——不存在中间状态。

## 编写之前

- **先阅读周边代码。** 在向一个文件添加代码之前，先阅读该文件、一个承担类似职责的邻近文件，以及项目自身的规则（README、现有测试）。了解其命名方式、错误处理惯例、注释密度与测试组织方式。不要编写你尚未见过其惯例的代码。
- **位置由职责决定。** 代码应当放在其职责所在之处，而不是任务描述所指向之处。如果聚合逻辑属于统计模块，就应放入统计模块——即使需求文本写的是"放入报告"。若这出乎用户意料，仍应照做，并说明理由。
- **先搜索，再编写。** 在编写辅助函数、类型或常量之前，先用 grep 查找是否已有现成的。复用一个平庸的现成实现，也好过写出第二份；一旦出现两份，它们迟早会彼此偏离。实现一段有已知高效解法的逻辑时更是如此：优先选用成熟的专用库，胜过手写一个平庸而缓慢的替代品——高性能往往早已被封装好，只是需要先想到去找。

## 编写过程中

- **与既有风格保持一致。** 按照代码库既有的风格编写，而不是按个人偏好——即使某些地方你认为自己的写法更好。风格一致是给下一位读者的礼物。如果既有风格确实已经损坏，应当指出问题，而不是不动声色地引入第二种风格。
- **注释默认要写。** 注释是常态，不是例外；与既有风格冲突时，以本条为准。分三层：文件开头说明该文件的职责；每个函数头说明用途与契约（输入、输出、副作用与错误行为）；每个逻辑段以注释开头，说明这一段的目的与它在整体中的角色。注释不逐句翻译代码，不复述语句已经表达的操作细节。注释与代码同生共死：代码变化，相关注释同步更新；过时的注释比没有注释更有害，宁删勿留。注释语言与代码库保持一致。
- **代码按逻辑段组织。** 每段承载一个完整的意图，段内语句紧凑，段与段之间以空行分隔。划分的判据是意义，不是长度——不为美观强行切分，不为节省行数强行合并。一段若写不出有信息量的注释，说明它没有划分好：与相邻段合并，或拆得更清晰。
- **规模适度。** 不做超出当下需求的抽象，不为单一调用方添加配置，不为不可能出现的状态编写防御分支；同样，凡是拆成几个命名清晰的步骤就能表达清楚的逻辑，不要堆进一个 200 行的函数；已有共享辅助函数时，不要复制粘贴。过度设计与设计不足同样是混乱。当用户明确要求快速实现或一次性产物时，应当遵从——小脚本同样需要清晰的命名、不留残余，只是不需要架构。
- **性能的常识判断。** 对性能代价保持敏感：不重复计算，不做无谓的拷贝，不在循环里做 I/O 或逐条查询，不选与数据规模不相称的数据结构或算法。这类判断靠常识，不必测量——拿不准时，只问一句"它会以多大的规模发生"。但**前提始终是可读性**：性能与清晰冲突时，除非确有理由认定这是热点路径，否则宁可清楚一点——不为想象中的性能，牺牲眼前的清晰。
- **有始有终。** 不留半成品实现，不留会悄然腐化的"暂且如此"，不留未经用户同意的 TODO。若要把事情真正做完，需要比需求多走一步，要么走这一步，要么在报告中明确指出——绝不要将其埋进代码里。
- **删除须彻底。** 已删除的代码应保持删除：不保留注释掉的旧代码，不留"// removed X"式的说明；未使用的参数、import 与变量应当删除，而不是改名以下划线掩盖。

## 路径内的修复

直接位于改动路径上的混乱，应当随改动一并修复。符合修复条件的情形：必须触碰的代码，按当前职责而言组织方式有误；其中存在真实的重复（或死分支），若不修复，你的改动会将其进一步放大；或者它直接阻碍了一个优雅的实现。

- **不越出路径。** 活动范围限于本次任务本就涉及的职责、文件与调用路径。顺手打开的不相关代码、你到来之前就已存在的文件，都应保持原样——值得指出即在报告中说明，但删除他人的内容不属于清理。
- **保持行为不变。** 清理不应改变代码的行为。若在任务范围之外发现真正的缺陷，应当报告，而不是悄悄修复。
- **让清理清晰可辨。** 遵循项目自身的组织原则，并使清理在 diff 中与行为变更清晰可分。
- **在报告中说明。** 报告的结尾应写明你修复了什么、为什么。未经声明的重构，与未经声明的混乱同样失当。
- **适时止步。** 如果整个模块的混乱远超你的路径，不要将其作为附带任务推倒重建——说出你所见，并提出后续建议。

## 宣布完成之前

1. **重读自己的 diff**，逐个 hunk 审阅，以下一位维护者的视角。凡有读来不妥之处，立即修正。
2. **清扫副产物**——临时脚本、临时文件、调试输出、下载的产物、测试残留。你造成的混乱，不应由用户收拾。
3. **按项目的方式验证**——测试、构建、lint——覆盖你修改过的代码；项目惯例要求补测试之处，补充测试。
4. **报告**——改动了什么，主动修复了什么，有意未动什么。

## 混乱的常见形态

- 某个模块已经负责该逻辑，辅助函数却被写在第一个调用者旁边。
- 同一事实被手工写成 N 份需要同步的副本——一条校验规则存在于三个文件中，一组允许值存在于四个地方。
- 因为"搜索不如直接写来得快"而出现的第二份日期解析代码。
- 遗留在路径上的调试输出；层层叠叠的 `console.log`。
- 注释掉的旧代码、`_ = unused`、"removed X" 式的墓碑。
- 仓库根目录遗留的 `scratch.py`、`test.json`、`fix2.js`。
- 功能被添加进当时恰好在编辑的文件，放错了层次。
- 行为变更被夹带在一次"清理"之中。
- 以 TODO 标记的半成品功能，下一位读者却会信以为真。

当上述任一症状被认出——或遇到不符合任何一条的混乱——请阅读 [references/anti-patterns.md](references/anti-patterns.md)：清单背后的几种通用形态、它们如何逐渐累积，以及如何在不偏离路径的前提下修复它们。
