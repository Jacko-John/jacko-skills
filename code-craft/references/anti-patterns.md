# 反模式详解

技能中的混乱清单列举的是症状，症状背后是少数几种通用形态。应当掌握这些形态——同一形态在不同代码库中会以不同面貌出现，而具体的面貌并不重要。

## 形态一 —— 同一事实的 N 份手写副本

同一事实在多处被手工写出，形成 N 份副本。N 通常为三。按惯例，其中一份充当"正本"，但没有任何机制保证这一点；其余各份依靠人的记忆保持同步。

**典型表现：** 修改一个小处，需要编辑多个互不引用的位置；遗漏其中一处，在你恰好测试到的那条路径上，一切仍然正常。

**它藏在哪里**——同一种弊病，表现在不同部位：

- 校验：一条输入规则写在解析器中，又写在校验器中，还出现在错误信息或文档里。
- 允许值：一个常量或类型、一张 switch 或 handler 映射表、一份测试夹具列表、一张界面文案表。
- 配置：选项定义在解析器中，默认值在另一处，文档在第三处。
- 传输格式：结构体的字段、手工编写的序列化器、对端期望的 schema。
- 存储：建表语句中的列集合、读写与复制路径使用的列清单、升级旧存储时补充的条目。
- 报表或界面：两个"几乎相同"的构建函数，第二个由第一个复制而来。

**为什么有害。** 不同的副本由不同的路径执行——创建路径与维护路径、写路径与读路径、生产方与消费方、代码与其测试或文档。这些副本彼此不相邻，没有任何力量强制它们保持一致；它们会一直一致，直到某天不再一致，而分歧将在生产环境中、在无人经过的路径上暴露出来。与此同时，每一次修改都要付出 N 倍的代价，每一位读者都必须记住 N 个位置。

**干净的形态。** 找到那个可供其余各份派生的表示，并让它们真正由它派生。一份定义加上几行生成代码，胜过 N 份需要同步编辑的列表。如果该事实确实必须存在于两个分离的世界中（生产方使用一种语言，消费方使用另一种），应当由一份生成另一份，或让两者互相校验——绝不手工维护两份。

## 形态二 —— 历史固化为机制

每一桩过往事故都被保留为专属的永久机制，并以事件命名：每次重写配一套定制迁移，每个旧客户端配一个分支，每种遗留格式配一个开关。这段历史被永远重演，名字连起来读，像一份变更日志。

**典型表现：** 名字描述的是事件而非职责（`convert_*`、`handle_legacy_*`、`..._v1`）；初始化代码一半用于定义当下，一半用于弥补过去；同一项工作的两套机制不共享任何手法。

**为什么有害。** 事故是数据，机制是代码。一桩被定格的事故需要被永远阅读下去，无法被概括、排序或整体退役——每出现一桩新事故，就新增一块定制代码，而不是扩充那个由数据驱动的通用机制。最终，文件不再有任何组织原则，每一位读者都必须先逆向还原这段历史，才敢相信眼前的内容。

**干净的形态。** 把历史表达为数据，交由一套通用机制遍历——一份有序的步骤列表、一张规则表、一个注册表——同一项工作只使用一种手法。当存储的内容可以派生或重建时，最诚实的策略往往是"期望值 ≠ 已存值 → 重建"，而不是逐事故的考古式升级；只有在数据珍贵、且旧版本能够跳过中间升级步骤时，才值得保留考古。即使"定义当下"与"了结过去"运行在同一条流水线上，也应将其视为两项独立的职责。

## 形态三 —— 接口的通货膨胀

一个操作被拆成多个入口，每个入口只服务于一种想象中的调用方式：`parse`、`try_parse`、`parse_or_default`；同步与异步各一套；抛异常版与返回默认值版并存；参数表里排着一串从未被传入的开关、回调与默认值。每个入口都带着自己的校验、兜底与文档，彼此真正的差异却只存在于名字里。

**典型表现：** 搜索一个函数名会得到多个“差不多”的定义；调用方要先读完文档才知道该用哪一个；修改行为时得同步改三份入口；某个参数从第一天起就没有调用方传过。

**为什么有害。** 接口是承诺。每多一个入口，就多一份需要维护、测试与解释的契约，也多一个让调用方选错的机会。冗余接口不会让代码更健壮，只会把“该做什么”的决定推给每一位读者。层层校验、处处兜底、参数可选——这类防御往往只是把内部的不信任写进了公开表面，而真正的信任边界反倒没有校验。

**干净的形态。** 一个操作一个入口，一条清晰的契约：边界处校验一次，内部信任类型与不变量；确有第二种真实用法时，再把它显式加进来，而不是提前预留。接口应当让正确的用法顺手、错误的用法难以表达；做不到这一点时，先修契约，再加变体。

## 遇到这些形态时

如果形态正位于你的路径上，它就符合修复条件：当你的改动触及其中任何一份副本、任何一段固化的机制，向干净形态靠近就是一次合格的路径内修复——保持行为完全一致，并在报告中说明所做的工作。如果形态远在你的路径之外，不要将其作为附带任务重建：说出你所见，并提出后续建议。
